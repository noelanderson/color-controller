## Functional Specification

### Problem Statement

Preset edits and the active solid color are lost whenever the controller
reboots or loses power. Users expect a wall controller to retain intentional
choices without preserving transient colors generated by animated modes.

### Proposed Solution

Store P1-P4 in ESP32 Preferences/NVS immediately after a successful long press.
Store the active solid color only after a manual wheel or preset selection has
remained unchanged for at least two minutes. Restore all valid saved values at
startup in solid mode. Entering rainbow or music cancels a pending active-color
save, so generated colors never become startup state.

Fixed-memory SimpleAwait C++20 tasks own touch, display refresh, audio
sequencing, effect frames, and the low-frequency persistence stability check.
Arduino `loop()` only polls the scheduler.

### Functional Requirements

- [x] P1-P4 survive reboot and power loss.
- [x] Presets are written when the `SAVED` confirmation is produced.
- [x] Wheel and preset selections are eligible for delayed selected-color storage.
- [x] Every manual color change restarts the two-minute stability period.
- [x] Rainbow and music mode entry cancels pending selected-color storage.
- [x] Startup restores valid values without immediately rewriting them.
- [x] Missing or invalid data falls back to firmware defaults.
- [x] Brightness, power state, and active effect mode are not persisted.

### User Scenarios

1. **Persistent preset:** Store a color in P1, power-cycle, and recall the same color.
2. **Stable selected color:** Select a wheel color, wait two minutes, power-cycle,
   and start with that solid color.
3. **Changed before deadline:** Select several colors within two minutes; only
   the last one becomes eligible after its own full stability period.
4. **Effect cancellation:** Select a solid color, enter rainbow or music before
   two minutes, and reboot without saving an effect-generated color.

### Out of Scope

- Persisting brightness, power, music/rainbow mode, effect phase, or sensitivity.
- User-visible reset-to-defaults controls.
- Migrating data from any earlier persistence schema.

### Open Questions (Functional)

- [ ] Confirm persistence behavior through physical power removal, not only reset.

## Technical Specification

### Architecture Impact

`PersistentState` owns the Preferences namespace and deduplicates writes.
`ManualColorSaveTracker` is a hardware-independent rollover-safe policy object.
Five SimpleAwait tasks own touch handling, LED effects, effect UI refresh,
audio initialization/feedback, and persistence. The persistence task polls its
policy every 250 ms and performs the NVS write after 120 seconds.
`ControllerModel` exposes bounded preset restoration.

### Dependencies

- **Internal:** `ControllerModel`, `ColorMath`, `Config`, and the main sketch.
- **External:** ESP32 Preferences/NVS and vendored SimpleAwait merged commit
  `765b418` (package metadata 1.0.1).

### Technical Requirements

- [x] Encode RGB in a stable 24-bit value rather than persisting object layout.
- [x] Use a namespace and keys within ESP32 Preferences limits.
- [x] Deduplicate identical values to limit flash wear.
- [x] Use unsigned elapsed-time arithmetic across `millis()` rollover.
- [x] Configure SimpleAwait for six task slots and a 2048-byte fixed frame pool.
- [x] Surface Preferences initialization and write failures over Serial.
- [x] Preserve NVS during normal policy-safe uploads by flashing discrete images.

### Implementation Considerations

- **Approach:** Immediate preset writes plus delayed selected-color writes balance
  predictable behavior and flash endurance.
- **Risks:** Flash corruption or incompatible future schemas must fall back
  safely. Full-chip/merged-image flashing intentionally erases NVS.
- **Alternatives considered:** A hand-written timer state machine would work,
  but the user explicitly requested SimpleAwait and the delayed save maps
  cleanly to a cooperative coroutine. Persisting on every drag update would
  create unacceptable write amplification.

## Feature-Specific Context

### Requirements & Constraints

- Presets persist across reboot and power cycles.
- A manually selected color persists only after at least two unchanged minutes.
- Music and rainbow colors must never be saved.
- Use native C++20 coroutines through SimpleAwait.

### Implementation Guidance

- Pin SimpleAwait to merged commit `765b418` and vendor it with its MIT license.
- Keep `loop()` limited to `simpleawait::poll_and_wait()` and run all periodic work as
  cooperative tasks.
- Preserve existing UI and mode transitions.

## Learnings & Notes

### Patterns Discovered

- ESP32 Arduino core 3.3.12 already compiles sketches and libraries as C++20.
- Fixed-memory tasks provide one scheduling model for persistence, touch,
  effects, UI refresh, and audio sequencing.
- Segmented uploads preserve NVS; flashing the padded merged image erases it.

### Issues Encountered

- The policy-safe uploader originally wrote the complete 16 MB merged image and
  required conversion to standard segmented flashing before persistence shipped.
- Review identified effect exit by preset hold, transient NVS failure retries,
  coroutine error handling, and merged-image documentation as edge cases; all
  were corrected before final validation.
- The pinned SimpleAwait commit labels its package metadata as 1.0.1 while its
  upstream `version.h` constant remains 1.0.0.
- The vendored snapshot uses upstream `poll_and_wait()` to block on a static
  FreeRTOS semaphore until the next timer or external signal. It retains a
  one-tick fallback when neither wake source exists so ESP-IDF driver work such
  as touch processing can continue.

### Notes for Future Work

- Add a schema version only when stored data expands beyond independent RGB keys.
- A future settings screen could expose reset-to-defaults without changing keys.
